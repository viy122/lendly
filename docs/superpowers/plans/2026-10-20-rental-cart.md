# Rental cart and owner review queue

User request: a Shopee-style cart that fits the rental system. The user selected an arrival-ordered review queue where the owner still chooses whom to approve. No strict FIFO approval gate or automatic waitlist promotion.

Flow: collect rental drafts with dates and pickup/delivery, review a cart grouped by owner, select items and send separate rental requests. Adding to cart reserves nothing and sends no notifications. Queue arrival is request submission time. Existing owner approval/date holds, bilateral saved agreements and per-booking wallet/payment verification stay in place. No quantities, combined payment or shopping order model: a listing represents one physical item.

Data: `cart_items` with id, user_id FK, listing_id FK, start_date, end_date, fulfillment_method, JSON terms snapshot and timestamps; unique(user_id,listing_id). Cart references may cascade on hard deletion (drafts only); soft-removed listings remain visible as unavailable until removed by renter. Terms snapshot has the same price_per_day/security_deposit/rental_rules/commission_rate shape as the existing request form. Derive every amount and owner from server data.

Shared request service (backend worker): `RentalRequestSubmission::termsFor(Listing): array`; `preview(User $renter, int $listingId, array $details): array` returns `listing` (fresh model), `terms`, and authoritative rental-request `attributes`; `submit(User $renter, int $listingId, array $details, array $presentedTerms, bool $accepted): RentalRequest`. Both entrypoints lock participants then listing, validate authorization/current account state, dates/window/duration/fulfillment/approved overlaps and compute charges. Submit additionally checks presented terms and review checkbox and sends existing notifications. Existing Create UI delegates submit and preserves its refresh/reset-on-repricing behavior. Do not duplicate request creation rules in the cart.

Cart service/component (cart worker): `RentalCart::save(User $renter, int $listingId, array $details): CartItem` calls preview, upserts a draft from the authoritative quote; `update(User $renter,int $cartItemId,array $details): CartItem`; `remove(User,int): void`; `checkout(User,array $selectedIds,bool $accepted): array` returns submitted request IDs. Checkout is all-or-nothing, removes only selected successful rows, preserves unselected/failed drafts, and prevents repeat submission through consumed cart rows and locks. Prelock all participating user IDs and listing IDs in sorted order before selected cart rows, matching the shared service order; derive scope from auth. Revalidate every selected row. Changed price/rules/rate must update the quote for review and fail that checkout with acceptance cleared; no silent changed charge. No cart money fields or owner IDs are accepted from the client. Reject oversized/malformed selections; reasonable cap 50 items.

`App\Livewire\Renter\Cart\Index`: properties `selected` array, `edits` array keyed item ID (start_date/end_date/fulfillment_method), `accept_terms` bool. Actions `updateItem(int)`, `remove(int)`, `checkout()`, `selectAll()`, `selectOwner(int)`; render variables `items` (cart rows eager-loaded listing.images/owner), `groups` (groupBy listing.owner_id), `selectedTotal` numeric. Mount selects all rows and fills editable dates; membership/auth refreshed each action; quantity one. Updating or selecting resets acceptance. Checkout redirects renter.rental-requests.index after success; validation errors remain in cart, grouped/item-specific explanation. No owner payment information appears before a booking.

Root: CartItem model/migration; Add to cart action in existing date modal (calls RentalCart::save, no terms acceptance required just to save); routes/navigation/cart count; owner pending queue ASC(created_at,id) while history remains DESC; queue copy and submission times; account-deletion draft cleanup; integration/security/queue tests and final checks.

UI worker: new cart Blade and Add to cart control in shared request form, using the above component contract. Listing CTA still opens the date form, containing both Add to cart and existing direct Send rental request. Cart resembles grouped seller rows with selection, image, dates, handover, daily rate, inclusive days, deposit/platform fee/total, remove and sticky selected summary. Dates and rates remain estimates until validated; requests need owner approval; each accepted booking is paid separately. No new dependencies or CSS system.

Ownership: backend worker owns app/Services/RentalRequestSubmission.php and app/Livewire/RentalRequests/Create.php + tests/Feature/RentalRequestSubmissionTest.php. Cart worker owns app/Services/RentalCart.php, app/Livewire/Renter/Cart/Index.php + tests/Feature/RentalCartTest.php. UI worker owns resources/views/livewire/renter/cart/index.blade.php and resources/views/livewire/rental-requests/create.blade.php. Root owns other changes. Root adds Create::addToCart only after backend edits settle to avoid collisions.

Verify direct-request regressions, cart persistence/isolation/id tampering, duplicate add/update, quotes changing, stale dates/listings/overlaps, atomic selected-only checkout, repeat checkout, no holds/notifications on add, same timestamps queue tie ordering, non-pending historical order, owner free choice of later request. Apply migration locally. Use separate compiled-view cache folders for concurrent PHP tests on Windows; never run frontend build while its scanned view cache is being mutated. No real identity or payment transaction is required.
